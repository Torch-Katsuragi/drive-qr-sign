# 設計

技術面の一次情報はこのファイル。事業・導入判断の一次情報はリポジトリ外（作者のノート）にある。

## 何を作るか

紙で回覧している書類の「押印」だけを電子署名に置き換える。書類は Google Drive に置いたまま動かさない。
印刷した QR をスマホで読むと署名ページが開き、Google ログイン後ワンタップで PAdES 署名とタイムスタンプが
PDF に埋まる。

一行で言うと「LibreSign の Google Drive 版」。

```
書類PDFをDriveに配置 → QR付きで印刷して紙で回覧 → 読了後にQRをスマホで読む
  → 署名ページ（Googleログイン）→ アプリがDrive APIでPDF取得 → 内容確認して署名（PAdES + TSA）
```

Drive のリンクから直接署名ページを開く経路も残す（QR は入口の一つでしかない）。

## 設計の柱

### 1. 署名の中身は標準技術に乗せる

自作の範囲はワークフロー（QR・署名ページ・Drive 連携）に限定する。署名そのものは既製の標準に乗せる。

- 署名形式は PAdES（pyHanko）。検証は Adobe Acrobat の署名パネルで誰でもできる
- タイムスタンプは RFC 3161 TSA
- 可視署名は印影画像のみを既存の押印枠に置き、紙面は従来と同じ見た目にする。
  時刻・署名者・改ざん検知はデータ層が持つ、という二層構成

証跡は PDF 自体に埋まるので、将来このアプリを廃止しても署名済み PDF 単体で検証できる。
これは「アプリに依存しない」という約束であり、設計上の最優先事項。

### 2. PDF が署名欄を自己記述する

署名欄の位置をアプリが知っている構成にすると、書類の種類が増えるたびにアプリを直すことになる。
そうならないよう、位置情報は PDF 側に持たせる。

- 書類生成側（Typst）で押印枠にラベル付きアンカーを仕込む:
  `#context metadata(here().position()) <sig-役職>`
- `typst query` でページ番号と座標を取り出す
- ビルド時にその座標へ pyHanko で空の署名フィールドを注入する。フィールド名はそのまま役職名。
  サイドカーファイルは不要で、Acrobat からも標準の署名欄として見える
- アプリが持つのは「メールアドレス → 役職」の対応表だけ。ログインすると本人の欄が自動で選ばれる。
  アプリは書類の種類を知らない

枠のない書類は、右上から右詰めで署名順に並べる既定ルールで座標を決める。

Typst 座標系は左上原点・単位は pt、PDF は左下原点なので、変換が要る（`typst_anchor` モジュールの責任範囲）。

### 3. OAuth は署名者に Drive スコープを要求しない

無料 Gmail アカウントの署名者もサポートするための要。ここが崩れると導入できる組織が激減する。

- 署名者の OAuth スコープは `openid` + `email` のみ（非センシティブ）。
  未審査の External アプリでも警告画面なしの通常ログインになる
- Drive アクセスは導入組織の管理用アカウントが一度だけ承認し、refresh token をアプリが保持する
  （本番は Secret Manager）。未審査アプリの警告突破は管理者の初回一回だけ
- 署名可否は「OpenID の検証済みメール」×「PDF 内の署名フィールド割当」の突合でアプリが強制する
- QR ペイロードは HMAC で署名し、偽造 URL・改ざん QR を弾く

> [!WARNING] この設計の代償
> Drive 用の認証情報を一つ預かるため、完全なステートレスではない。
> アクセス制御の根拠が「署名者本人の Drive ACL」から「アプリによる突合」に移る。
> 導入者はこれを理解した上で使うこと。README にも明記する。

### 4. 導入モデルは組織ごとのセルフホスト

未審査 External アプリには生涯 100 ユーザーの上限があるため、共有ホスト型のサービスにはできない。
導入組織ごとに、自組織の GCP プロジェクトと OAuth クライアントを持つ。

- Workspace 組織は Internal 登録（警告ゼロ・上限なし）、無料アカウント混在の組織は External 登録。
  コードは共通
- プロジェクト作成からデプロイまでは gcloud で自動化できるが、
  OAuth 同意画面とクライアントの新規作成は API が開放されておらず（Terraform でも不可）
  コンソールでの手作業が残る
- したがって公開物は「アプリ本体 + 導入・運用を自動化する Claude Code 用スキル」のセット。
  スキルは 9 割自動、同意画面のところだけ人間をガイドする半自動構成

## 実装の順序

1. 署名コア（PAdES + TSA + 空フィールドへの署名）— pyHanko の薄いラッパ
2. Typst アンカー → 座標 → 空署名フィールド注入
3. 署名ページ（FastAPI）+ Google OIDC + Drive 読み書き
4. QR ペイロードの HMAC と、QR を焼き込んだ状態でのビルド
5. Cloud Run へのデプロイと、導入スキル

file ID の鶏卵問題（QR に URL を焼くには file ID が要るが、ID はアップロード後にしか決まらない）は
Drive API の `files.generateIds` で解く。先に ID を予約 → URL と QR を焼き込んでコンパイル →
予約した ID で `files.create`。後から埋め込む工程を作らない。

## 未決事項とプロトタイプでの既定値

| # | 論点 | プロトタイプの既定 | 本番で決めること |
|---|---|---|---|
| 1 | TSA | freeTSA（`https://freetsa.org/tsr`） | 検査での説明力を優先するなら総務大臣認定の国内 TSA |
| 2 | 署名鍵 | 自己署名の開発用証明書 | 自己署名だと Acrobat が警告を出す。許容するか AATL 掲載 CA から買うか |
| 3 | 署名済み PDF の書き戻し | 別名保存 | 元ファイルへの増分更新にして Drive の版管理に乗せる案がある |
| 4 | ホスティング | ローカル（uvicorn） | Cloud Run 無料枠を想定。GAS は PDF 操作が弱く不向き |

いずれも 1 と 2 は差し替え可能な形（TSA は URL、鍵は証明書ファイル）に閉じ込めてあるので、
後から決めても実装は動かさなくてよい。

## 近縁 OSS との違い

| OSS | 近い点 | 決定的な違い |
|---|---|---|
| Scan Me（Frappe アプリ） | pyHanko PAdES・印刷書類の QR・複数署名者 | QR の用途が「検証」入口。Frappe スタック内に書類が住む |
| LibreSign（Nextcloud） | 書類を自分のストレージから動かさない思想 | Nextcloud 専用。Drive 向けは空席 |
| Documenso | PAdES 署名（P12 / Google Cloud KMS） | DB 持ちのプラットフォーム型 |
| DocuSeal | API 座標指定・監査証跡 | GCS/S3 対応はアプリの倉庫であってユーザーの Drive ではない |
| Google Drive eSignature | Drive 内完結・追加費用なし | API 非対応で毎回手動配置、QR 不可、PAdES 非対応、本人性はメールリンクのみ |

本設計の空席は「Drive 常駐 + Google ログイン + QR から署名アクション + ほぼステートレス」の 4 点セット。
既存 OSS の fork ではなく新規実装とする。近縁はいずれも状態を抱えるプラットフォーム型で背骨が違うため、
再利用はライブラリ層（pyHanko・Google SDK）に留める。ライセンスも近縁の AGPL に縛られない。
